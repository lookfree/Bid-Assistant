# spec334 标书分类（货物 / 服务 / 工程）：判定 + 人工纠偏 + 分类化生成与审查 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development 逐任务执行。

**Goal:** 把「这是一本什么类型的标书」变成贯穿全链路的一等维度。读标后系统给出判定（货物 / 服务 / 工程）与证据条款，用户在读标页确认或改判；确认后的分类下发给提纲、正文、审查、审核表四处，注入该类标书特有的**必备章节**与**必查项**。货物标漏了「中小企业声明函填列所有制造商」、工程标漏了「施工组织设计四大块」、服务标没识破「定人定薪」变相最低限价——都是通用提示词管不到、而后果直达废标或利润归零的知识。

**Architecture:** 与 spec324 选包同构，逐点复用其管线。`ReadResult` 增 `bid_category`（系统判定值 +
置信度 + 证据条款，**读标收尾的一次轻量结构化模型调用**）；项目表增 `bid_category` 列（**用户确认值**，
与判定值分开存）；App 在 outline 及之后各步的 `run_input` 带 `bid_category`；agent 在**五个注入点**
（提纲 / 正文规划轮 / **正文子写手** / 审查 / 审核表接口）按类注入知识块。未判定 ⇒ 全链路行为与今天逐字节一致。

```
read 节点收尾
   ├─ 单包标书 ⇒ 一次轻量分类调用（喂读标结论摘要，非全文）
   │     └─ ReadResult.bid_category {value, confidence, reason, evidence_clause_ids}
   └─ 多包标书（packages > 1）⇒ 不判定，value=null      ← 此时系统还不知道用户要投哪个包
读标页
   ├─ 选包卡（spec324，多包时渲染）
   └─ 分类卡（**在选包卡下方**）
         └─ PATCH /projects/:id/category                 ← 用户确认/改判 → 项目行
         └─ 判定值 ≠ 确认值 ⇒ 记一条纠偏样本              ← 判定质量迭代的燃料
有效值 = 确认值 ?? 判定值  →  run_input.bid_category  +  命中的行业关键词补丁
   ├─ outline           ：该类必备章节自检清单（补漏，不覆盖招标文件构成清单）
   ├─ content 规划轮     ：章节层面的写作要点与陷阱
   ├─ content 子写手     ：落笔层面的要点  ← **拼进 subagent 的 system_prompt，不靠规划轮转述**
   ├─ review            ：该类必查项 + 行业资质补丁（须标注「经验≠明文要求」）
   └─ /generate/checklist：该类投递前核对项  ← **是同步接口不是图节点，没有 run_input**
```

## Global Constraints

- 作者 `lookfree <etwuman@126.com>`；禁止 Claude 相关内容。函数 ≤80 行、文件 ≤800 行。
- **有效值 = 用户确认值 ?? 系统判定值。判定值默认生效，不等用户点。**
  否则绝大多数用户根本不会点那张卡，功能等于没做。默认生效是安全的：分类只加提示词、不碰钱、
  带证据条款可查、随时可改判且改判后重跑即生效。前端文案必须诚实——写「系统判定：服务标 ·
  已按此生成（可修改）」，不能写成「请选择」却又在背后已经用上了。
- **未判定（`value=null`）时行为逐字节不变**——分类是加法，不是前置门槛。不像选包那样卡
  `package_required`：选包不选会拿错数据生成，分类判不出只是少一层增强。
  **不得因为缺分类就拒绝开跑。**
- **招标文件优先于分类知识**：类型必备章节清单只补招标文件**没提到**的章；凡 `required_structure`
  已给出的一律以招标文件为准。分类知识是行业经验，不是招标要求，二者冲突时经验让路。
- **必备章节一律是「投标文件」视角**。招标文件自身的必备章节（投标人须知前附表、澄清与修改、
  质疑与投诉…）是采购人视角，与本功能无关，混进来会把整张清单带偏。
- 分类**不额外计费**：判定调用只吃读标结论摘要（几 k tokens，相对读标本身可忽略），随读标步一并结算；
  下发只是提示词变长。**分类调用失败不得让读标步失败**——不能为一次锦上添花赔上一整轮读标费用。
- 迁移手写 SQL（沿 0026 惯例，drizzle snapshot 已滞后不可 db:generate）。
- 命名用 `bid_category` / `bidCategory`，**不用 `bidType`**——`apps/web/app/(tool)/content/page.tsx:70`
  的 `bidType` 已经是「技术标/商务标/全文」的 tab 键，同名两义必然出事。

### Task A: Agent — 分类判定（读标收尾的一次轻量模型调用）+ ReadResult 字段

**为什么用模型而不是关键词打分**：分类是**语义判断**，不是字面匹配。实测（见「未决问题」第 1 条）
关键词方案在我们自己的语料上判错了房地产开发项目、把「定制开发」判成货物——「定制开发属于服务」
这种事没有任何关键词抓得住。更要命的是维护成本：词表天然带着编写者所在行业的口音，换一个行业就要
重配一次，而模型天然泛化。**关键词只保留在「行业资质触发」上（见 Task B），那才是字面匹配任务。**

**调用形态（三条硬约束，缺一条就退回到当初否掉它的理由）：**
1. **不塞进 `submit_read_result`**——读标的提交工具 schema 已经很大，加字段有被小模型静默跳过的
   先例；分段并行 6 路还要额外定义合并语义。分类走**读标收尾的一次独立结构化调用**。
2. **喂读标结论摘要，不喂全文**：`project_meta` + 技术需求条目前 N 条 + 评分表类目 + `required_structure`
   标题列表，量级几 k tokens。读标本身是 6 路并行、百万字量级的调用，这次分类连 1% 都不到。
3. **必须回证据**：返回 `{value, confidence, reason, evidence_clause_ids}`，`evidence_clause_ids` 取自
   摘要里带的条款 id，前端可点开定位原文。**没有证据的判定不给用户看**——用户无从判断该不该改判。

**判定规则：**
- `value ∈ {goods, services, engineering} | null`；模型对判据不足的一律返回 `null`，**不许猜**。
- `confidence ∈ {high, medium, low}`；`low` 在前端等同于「请你确认」，不预选。
- **模型未配置 ⇒ 不判定（`value=null`），读标本身照常成功**。分类是加法，绝不能因为分类调用
  失败就把整个读标步拖失败——那会让用户为一次锦上添花的功能赔上一整轮读标费用。
  同理，分类调用抛错/超时一律吞掉记日志，`value=null` 交用户。

**多包件招标：不判定，直接交用户。** 时序上判定发生在选包**之前**——读标面向全文（`projects.ts`
明确：`package` 只对 `step≠read` 下发），此时系统还不知道用户要投哪个包。多包标的各包可能分属不同
类别（如包1设备采购、包2机房改造、包3运维服务），拿全文判出来的类别安到某个具体包上是错的。
`packages` 长度 > 1 时直接 `value=null`，前端分类卡渲染在选包卡下方、文案改为「请选择所投包件的类型」。

> **实测依据**：库里 3 份多包标（4 包的设备采购标、两份 3 包的服务标）各包同类，**跨类多包我们
> 一次都没观测到**。所以这里选的是最省的做法——多包时让用户点一下，而不是为一个没见过的场景
> 加「选包后重新判定」的链路。用户在那一页本来就要做选包动作，顺手选类型的成本极低。
> 若纠偏数据日后显示多包标用户总是选同一类，再考虑自动化不迟。
>
> 顺带记一个**当初关键词方案的结构性缺陷**：它对全文打分，导致同一份 4 包招标文件的「包件一」
> 与「包件四」得分逐位相同——那次两个包碰巧都是货物、结论对了，但方法本身拿不到包级输入。

**线下上传标书（`kind=review`）同样启用，但输入源与触发点按形态二选一。** 这类项目有两种形态
（`routes/projects.ts:455`）：带招标文件的 `status=draft / currentStep=read`，不带招标文件的
`status=running / currentStep=review`——**后者根本不跑 read，没有读标结论可喂**。

| 形态 | 分类输入 | 触发点 | 用户确认在哪 |
|---|---|---|---|
| 线下标书 + 招标文件（对照审查） | 读标结论摘要 | read 收尾 | 读标页分类卡（与生成流水线完全一致） |
| **线下标书，无招标文件（通用自查）** | **上传标书正文摘要**：`parse_bid_chapters` 解析出的章节标题清单 + 每章前若干字 | **review 节点开头，先分类再审查** | `/risk` 页分类卡（该项目没有读标页） |

> 第二种为什么放在节点开头而不是节点之后：放在之后，用户看到分类时这一轮审查已经跑完、**并没有
> 用上分类知识**，得再花一次钱重跑才生效。放在开头则当轮即用，用户事后改判、重跑才需要再付费。
>
> 判「投标文件」的类别比判「招标文件」更容易——一本工程标的正文里满是施工组织设计、工程量清单，
> 特征比招标文件更显性。

**判定值怎么回到 App 和前端（两条路径，均已核对现有代码，不需要改结果通道）：**

| | 生成流水线 / 带招标文件的线下标书 | 无招标文件的线下自查 |
|---|---|---|
| 判定发生在 | read 节点收尾 | review 节点开头 |
| 挂在哪 | `{"read": {**result.model_dump(), "doc_sections": clauses, "bid_category": cat}}` | `{"risk": {**result.model_dump(), "bid_category": cat}}` |
| App 怎么拿到 | `_RESULT_KEY["read"]="read"` → 落 `project_steps.result` | `_RESULT_KEY["review"]="risk"` → 同上 |
| 前端怎么拿到 | 该步 result 经 `toCamel` → `bidCategory` | 同左 |

三点关键，都**不是推断，是核对过的**：

1. **不进工具 schema。** `bid_category` 是**另一次调用**的产物，塞进 `submit_read_result` /
   `submit_risk_report` 就等于把它暴露在「小模型静默跳过字段」的风险下。做法沿用现成成例：
   `nodes/read.py:283` 已经在往 `model_dump()` 后的 dict 里塞 `doc_sections`——而 `ReadResult`
   **并没有** `doc_sections` 这个字段。schema 之外的键照样能随结果落库，这条路是通的。
2. **非会员裁剪不会吃掉它。** `lockRiskAdvice`（`entitlements.ts:44`）是 `{...r, items, adviceLocked}`
   展开式，不是白名单重建，未知键原样透传。（这一条必须核对而不能假设：白名单式重建静默丢字段
   的坑本仓库刚踩过。）
3. **App 侧读判定值只取那一个 JSON 键，不拉整列 result。** 照抄多包件门禁的现成写法
   （`projects.ts:706` 的 `select result -> 'packages'`）——大标书 read result 可达 1MB，
   绝不为一个标量把整列拖过隧道。

**重跑时不重复判定：** App 下发 `run_input.bid_category` 后，节点直接用，**跳过分类调用**。
用户改判过的项目重跑，用的是他改判后的值，且不会被系统再判一次覆盖。

### Task B: Agent — 分类知识注入 + 行业关键词补丁

知识分**两层，但只有一层需要建模**：

| 层 | 承载什么 | 形态 | 为什么这样 |
|---|---|---|---|
| 类别（三选一） | **结构性**差异：必备章节、施工组织设计四大块、声明函填法 | 三个知识块 | 三类之间结构差异稳定、可穷举 |
| 行业 | 特有**资质**与**陷阱** | 一张 `关键词 → 必查项` 补丁表 | 子类型多到无法穷举，**不建行业层** |
| 长尾 | 该行业该写什么内容 | **不做**——已有 | `prompts/outline.py` 第 5 条已强制「提纲覆盖评分办法表每个得分点」，从评分项反推本就是现成能力 |

**三类知识初稿**（来源见「未决问题」第 1 条，落地前需业务确认）：

> **验证状态标记（贯穿本节）**：每条知识都带一个状态——`待验证` = 来自行业通行做法整理，
> 尚未用真实标书核对；`已验证` = 已在我们自己的语料/客户实践中核对过。**`待验证` 的条目不得
> 以「必备/必须」的口吻进提示词**，只能作为「请核对是否需要」的提示。理由见「决策记录」的
> 「知识分级落地」一条：错的必备清单比没有清单更糟。当前全部条目均为 `待验证`。

**#3 是本 Task 最容易做错、且错了会静默失效的一处。** `content` 是 deepagent：规划轮
(`CONTENT_PLANNER_PROMPT`) 负责派活，真正落笔的是子写手 (`CHAPTER_WRITER_PROMPT`)。
只把要点加在规划轮的 user 消息里，**能不能到子写手完全取决于规划轮肯不肯转述**——这正是
`desc` 踩过的坑（`prompts/content.py` 里那句「必须原样转述给子写手…丢掉等于把用户的意图默默扔了」
就是事后补的）。子写手的 `system_prompt` 是在节点内构造 `create_deep_agent` 时传入的，
**可以动态拼接**，不必依赖转述。规划轮那份（#2）仍要给，但只负责章节层面的取舍。

**#5 是接口而非节点。** `POST /generate/checklist` 同步无状态、不进 thread、**没有 `run_input`**，
body 只有 `read_result` + `model`（`routes/generate.py`）。所以：
- body 增可选 `bid_category`，由 App 下发**有效值**（确认值 ?? 判定值）；
- 不传时回落到 `read_result.bid_category`（判定值本来就在里面），`_slim_for_checklist` 一并带出；
- **不能只靠回落**——用户改判后的确认值不在 read result 里，只走回落等于改判对审核表不生效。

**审查那处的口径必须写死**：「这些是行业经验必查项，**不是本次招标的明文要求**：能对上招标条款的
按高风险报，对不上的按中风险提醒」。否则会把经验当红线，刷出一堆招标文件根本没要求的「废标风险」，
用户信错一次就再也不信体检报告了。

## 决策记录

- **判定用模型，不用关键词打分（本条为改判，先前结论已作废）**。
  先前定的是确定性关键词打分，理由是「可单测、可给证据、零 token、read 的 schema 加字段有风险」。
  实测把前三条都推翻了：
  ① 关键词把一份**房地产开发项目**判成「服务」（工程侧命中 `分部分项工程/主体结构/施工现场` 却输给
     服务侧的 `人员配置/服务期/咨询/驻场`），把「统一身份认证平台升级改造（**定制开发**）」判成货物——
     **「定制开发属于服务」是语义，没有任何关键词抓得住**；
  ② 「可给证据」是假的：一份**网络攻防演练**标命中了「物业管理」，这种证据只会误导用户；
  ③ 「零 token」的分量被高估了——读标本身是 6 路并行、百万字量级，一次几 k tokens 的分类调用
     连 1% 都不到；
  ④ 唯一站得住的是「read 的提交 schema 加字段有被小模型静默跳过的先例」——但那反对的是
     **实现方式**（塞进 `submit_read_result`），不是**要不要用模型**。改成读标收尾的独立调用即可绕开。
  还有一条实测才看清的：**词表天然带着编写者所在行业的口音**。手头那份词表偏物业后勤类
  （物业管理/保安/保洁/餐饮/护工），而我们的语料 12 份里 11 份是 IT 采购——换一个行业就要重配一次，
  而模型天然泛化。**关键词只留在「行业资质触发」上**（Task B），那才是字面匹配任务。
- **判不准就交给用户，不做兜底猜测**：与「模型未配置即 400、绝不静默回退默认模型」同一条铁律。
  静默的错误判定会把整本标书骨架带偏，用户还无从察觉。提示词里必须写死「判据不足一律返回 null，
  不许猜」。一个反面做法是「都不达标时取最高分、初值给某一类」：那让「不判定」这条路径永远走不到，
  判不准时不是不判，是**默认某一类**。
- **分类失败绝不拖垮读标步**：模型未配置、调用超时、返回不合法，一律吞掉记日志并置 `value=null`。
  读标是这条链上最贵的一步，为一次锦上添花的分类赔上整轮读标费用是不可接受的。审查步同理。
- **线下自查项目的分类也走模型，而不是让用户在上传时选**：后者更省（用户上传自己的标书，当然知道
  是什么类型），但会让「AI 判 + 人工纠偏」这条主线在两个入口上不一致，用户得学两套交互；
  而分类调用本身相对审查步的成本可忽略。选一致。
- **多包件不自动判、直接交用户**：判定发生在选包**之前**（读标面向全文，`package` 只对 `step≠read`
  下发），此时系统还不知道用户投哪个包；各包可能分属不同类别，拿全文判出来安到某个包上是错的。
  实测库里 3 份多包标各包同类、**跨类多包一次都没观测到**，所以不为这个没见过的场景加
  「选包后重新判定」的链路——用户在那一页本来就要选包，顺手选类型成本极低。
- **不建行业知识层**：服务标子类型多到无法穷举（保安/保洁/食堂/会务/绿化/护工/救生员/物流/检测/品牌推广…），
  逐个建模是无底洞。行业维度只做「关键词 → 资质必查项」的补丁表，内容层面靠评分项反推兜底。
- **知识分级落地（`待验证` / `已验证`）**：三类清单里的每一条都带验证状态，**未经真实标书核对的条目
  不得以「必备/必须」的口吻进提示词**，只能作为「请核对是否需要」的提示。理由：写手对提示词里的
  「必备」是无条件服从的，一条错的必备章节会让每一本标书都多出一章不该有的内容，而用户看不出
  那是我们编的还是招标文件要求的。**错的清单比没有清单更糟。**验证一条、转正一条。
- **人工纠偏必须回流**：改判即样本，运营可见。否则每个用户重复纠同一个错，而我们永远不知道。
- **判定值与确认值分两处存**：合并成一列的话，重跑读标会把用户的改判悄悄冲掉。
- **分类是加法不是门槛**：没分类只是少一层增强，卡住等于给所有存量项目加了一道新门。
- **不做分类默认评分权重（价格分/技术分占比）**：评分表来自招标文件原文抽取，
  再塞一套行业默认权重只会和真实评分表打架；最低价法项目本来也不需要权重。
- **命名 `bid_category` 而非 `bid_type`**：`bidType` 在前端已占用为技术标/商务标。

   | 结果 | 数量 | 典型案例 |
   |---|---|---|
   | 判得对 | ~7 | 信息安全设备采购 → 货物；攻防演练服务 → 服务 |
   | **判错** | 1 | **房地产开发项目 → 判成「服务」**。工程侧命中 `分部分项工程/主体结构/施工现场`（6 分），却输给服务侧的 `人员配置/服务期/咨询/驻场`（8 分） |
   | 存疑 | 1 | 「统一身份认证平台升级改造（**定制开发**）」→ 判成货物；服务侧只命中一个「咨询」 |
   | 不判定 | 1 | 「零信任安全接入网关**建设工程**…采购」10:10 平手 → 交用户。**这份处理得对** |

   两个必须正视的问题：
   - **词表偏向物业后勤类**（物业管理/保安/保洁/餐饮/护工/档案整理），而实测语料 12 份里 **11 份是
     IT / 信息安全采购**。证据：一份**网络攻防演练**标命中了「物业管理」——纯噪声。IT 服务标真正的
     判别词（运维服务、驻场实施、技术支持、系统集成、定制开发、二次开发、需求调研）**几乎不在词表里**。
   - **三分法在 IT 采购内部区分度天然低**：一个平台采购 = 软硬件（货物）+ 部署实施（服务）+ 运维（服务），
     招标文件里必然同时出现「交货期/质保期/到货验收」和「服务期/运维服务/驻场」。那个 10:10 的平局
     不是算法没跑够，是业务本身就是混合的。

2. **战略问题：三分法对我们的客户结构是否够用？**（比第 1 条更上位，需产品决策）
   若客户以 IT 采购为主，三分法会把绝大多数标归进一两类，分流作用有限；而客户真正需要区分的
   （软件开发 / 系统集成 / 安全服务 / 设备采购 / 运维外包）三分法切不开。三个方向：

   | 方向 | 说明 |
   |---|---|
   | A 照做三分法 | 合规口径正确，对工程/物业/餐饮类客户价值大，对当前 IT 客户价值小 |
   | B 三分法 + IT 细分 | 三分法定结构（声明函填法、必备章节），IT 细分定内容；工作量最大 |
   | C 先不做分类，只做行业补丁表 | 跳过分类维度，直接做「关键词 → 资质/必查项」；成本最低，对 IT 客户立刻有用 |

   **前提事实待确认：实测样本来自单一客户（信息安全行业），不足以代表未来客户结构。**
